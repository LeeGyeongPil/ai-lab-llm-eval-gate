# 개념 노트 — 채점기를 고르는 법, 잡음을 읽는 법

evalgate 의 코드를 읽기 전에 알아 두면 좋은 개념 다섯 가지입니다. 수치는 2026-11-08 에 로컬(M3 16GB, Ollama 0.40.15, qwen3:4b, bge-m3)에서 직접 잰 값입니다. 공유 장비라 시간은 흔들립니다.

## 1. 결정적 채점 vs LLM 심판

| | 결정적(`exact`·`regex`·`contains`) | LLM 심판(`judge`) |
|---|---|---|
| 같은 입력 → 같은 점수 | 항상 | 아니오(온도·시드에 따라 흔들림) |
| 비용·속도 | 공짜, 즉시 | 모델 호출 1번(로컬 4B 생각 모델은 10~60초) |
| 약점 | 표현이 조금만 달라도 틀림 | 편향, 형식 오류, 느림 |

프로브에서 `대한민국의 수도는 **서울**입니다.` 같은 답은 정확 일치로는 0점이었고 심판은 PASS 였습니다. 반대로 심판만 쓰면 "분류: 배송" 같은 **형식**이 깨져도 눈치채지 못합니다. 그래서 이 도구는 형식과 라벨은 결정적 채점기(`format`, `label`)로, 정책 사실은 심판(`judge`)으로 나눠 맡깁니다.

정확 일치의 정규화(`scorers.normalize`)는 호환 문자 통일(`H₂O` → `H2O`), Markdown 강조(`**`) 제거, 공백·구두점 제거, 소문자화입니다. 너무 세게 정규화하면 틀린 답이 통과하므로 규칙을 테스트로 고정해 두었습니다.

## 2. 심판 쓰는 법과 편향

- **기준 정답 대조형 + 이진 판정**: "더 좋은 답을 골라라"가 아니라 "정책 사실과 맞는가? PASS/FAIL + 이유 한 줄". 1~5점 척도보다 안정적입니다.
- **정책 사실을 기준으로**: 쉬운 상식 문제(수도, 덧셈)는 두 프롬프트 모두 심판 1.00 으로 천장에 붙어 차이를 못 잡았습니다. 틀릴 여지가 있는 기준을 줘야 합니다.
- **판정을 못 읽으면 FAIL**: `판정: PASS|FAIL` 형식이 아니면 점수 0 + `parse_error` 로 기록합니다. 점수를 부풀리지 않기 위해서입니다.
- **알려진 편향**: 두 답을 비교시키면 순서에 따라 승자가 바뀌고(프로브: 3건 중 1건이 두 번 다 앞자리 답을 고름), 긴 답을 선호하며, 같은 계열 모델의 답을 후하게 줍니다. 완화책은 이진 판정, "길이·형식은 보지 말 것" 명시, 가능하면 피평가 모델과 다른 심판 모델(`EVALGATE_JUDGE_MODEL`)입니다. 이 도구는 쌍대 비교를 구현하지 않았습니다(다음 단계 후보).

## 3. 임베딩 유사도는 정답 판정에 쓰지 않는다

기준 문장 "파손된 상품은 무료로 교환해 드립니다."와의 bge-m3 코사인:

| 비교 문장 | 코사인 |
|---|---|
| 맞는 다른 표현 | 0.767 |
| **정반대**("교환이 불가능하며 환불만") | **0.734** |
| 무관한 문장 | 0.500 |

정반대 뜻과 맞는 표현의 차이가 0.03 입니다. 그래서 `on_topic`(similarity)은 "주제에서 벗어났는가"를 보는 **참고 지표**이고, 게이트 하한은 걸지 않았습니다.

## 4. 반복과 잡음

같은 프롬프트도 온도가 0 보다 크면 매번 답이 달라집니다. 그래서 케이스마다 `repeats` 번 돌려 평균을 냅니다.

- **표준오차는 케이스 단위로**: 케이스별 반복 평균을 먼저 구하고, 그 값들의 표준편차를 √(케이스 수)로 나눕니다. 같은 케이스를 여러 번 돌린 점수는 독립이 아니므로 반복 횟수로 나누면 오차를 작게 잡습니다(`stats.py`, Miller 2024).
- **잡음 범위 표시**: 기준선과의 차이가 **같은 케이스끼리 짝지은 차이의 표준오차 × 2** 이내면 보고서에 "잡음 범위"(`~`)로 표시합니다.
- **케이스가 8개면 한 케이스가 12.5%p** 입니다. 작은 점수 차이는 대부분 잡음이니 세트를 키우거나 반복을 늘리세요.

## 5. 생각 모델(thinking)과 평가

`qwen3:4b` 는 생각 전용 모델(Qwen3-4B-Thinking-2507)이라 어떤 방법으로도 생각을 끌 수 없었습니다.

- OpenAI 호환 `/v1` 을 쓰면 생각은 `message.reasoning` 으로 분리되고 `content` 에는 최종 답만 옵니다.
- Ollama 네이티브 `/api/chat` 에 `think:false` 를 주면 오히려 생각이 `content` 에 `</think>` 와 함께 섞였습니다. 그래서 `/v1` 만 쓰고, 혹시 섞여 오면 `</think>` 앞을 버리는 방어(`providers.strip_think`)도 둡니다.
- 온도 0 은 생각을 더 길게 만들었습니다(같은 심판 요청 22.6초 vs 0.6 에서 10.8초). 모델 권장값(온도 0.6, top_p 0.95)과 고정 시드를 씁니다.

## 큰 도구와의 대응

| evalgate | promptfoo | Inspect |
|---|---|---|
| `exact`·`regex`·`contains` | `equals`·`regex`·`contains` | `exact()`·`pattern()`·`includes()` |
| `similarity` | `similar` | (직접 구성) |
| `judge` | `llm-rubric` | `model_graded_qa()` |
| `repeats` + 표준오차 | `--repeat` | epochs + stderr |
| `--gate` 종료 코드 1 | 실패 시 exit 100, 통과율 임계값 | (직접 구성) |
| `--mode mock` 녹화 재생 | `echo` 공급자, 디스크 캐시 | `mockllm/model` |
